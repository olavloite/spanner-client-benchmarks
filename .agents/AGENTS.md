# Gemini & Jetski Developer Instructions

This repository contains multi-language benchmarks for Cloud Spanner. To maintain code quality, consistency, and build integrity, all Gemini model assistants, Jetski/Antigravity agents, and developer bots MUST adhere to the following rules and checklist before declaring a task as "done".

## 🚀 Benchmarking Guidelines

### Ad-hoc Benchmarks
When running manual, ad-hoc, or experimental benchmarks (either locally or on GCP):
* **Bypass Cleanup**: Always set the environment variable `SKIP_CLEANUP=true` to bypass the execution of the slow automated image/job cleanup script.
* **Alerting**: Ensure `FOR_ALERTING=false` (the default) is set so that experimental telemetry data does not affect production regression or alerting dashboard pipelines.

### Process Affinity & Sidecar CPU Pinning
When running sidecar-based benchmarks (`USE_SIDECAR=true`) on GCE VMs (`BENCHMARK_TARGET=gce`):
* **Do NOT manually manipulate core pinning**: The `entrypoint.sh` automatically detects the hyperthread core topology of the GCE VM, registers the workload generator strictly on CPU 0, and allocates the client runner to all other CPUs (`1..N-1`).
* **Starvation Prevention**: Single-threaded runtimes with helper thread pools (like Node.js with libuv crypto threads) require at least 3 vCPUs (i.e. `--cpu=4` mapping to `n2-standard-4` machines) to avoid internal CPU starvation and latency inflation. Avoid deploying sidecar Node benchmarks on `n2-standard-2` (2 vCPUs) machines.

### GCE VM Resource Naming
* **VM Instance Names**: GCE VM instance names are generated by `run_benchmark.sh` using the pattern `sb-$BENCHMARK_TYPE-$CLIENT_TYPE-$SIDECAR_LABEL-$SUFFIX`. The custom `--benchmark-name` flag does **NOT** affect the GCE VM resource name (it is only passed to the benchmark container internally). When writing monitoring tools or querying VM status, identify instances using the `sb-$BENCHMARK_TYPE` prefix and the unique timestamp suffix of the run.

## 📋 Pre-completion Checklist
Before you state that a task is complete, you **MUST** run the code formatters, linters, and **unit tests** for all languages and directories that you have touched.

### Formatting Commands by Language/Directory

#### ☕ Java (Directories: `java`, `analyzer`)
- **Action**: Run the formatter.
- **Command**:
  ```bash
  mvn fmt:format
  ```

#### 🐹 Go (Directory: `go`)
- **Action**: Run the formatter.
- **Command**:
  ```bash
  gofmt -s -w .
  ```

#### 🐍 Python (Directory: `python`)
- **Action**: Run the formatter and linter fix.
- **Command**:
  ```bash
  ruff format .
  ruff check --fix .
  ```

#### 📦 Node.js (Directory: `node`)
- **Action**: Run the formatter.
- **Command**:
  ```bash
  npm run format
  ```

#### 🦀 Rust (Directory: `rust`)
- **Action**: Run the formatter (Rust and TOML).
- **Command**:
  ```bash
  cargo fmt
  npx @taplo/cli fmt
  ```

### 🧪 Unit Testing Commands by Language/Directory

#### ☕ Java (Directory: `java`)

## 🛠️ Code Conventions & Rules

### 1. General Code Quality
* **Avoid Code Duplication**: Do not write duplicate code. Use idiomatic methods, helper functions, or abstractions (such as abstract base classes and interfaces) to share logic.
* **Keep Methods Small**: Avoid writing very large methods. Break down routines into small, focused, single-responsibility helper functions to keep code readable.
* **Manage File Size**: Do not create excessively large source files unless strictly necessary. Separate distinct business concerns and logic into distinct, modular files. Ensure code that naturally belongs together resides in the same file.
* **Idiomatic Code**: Always write clean, idiomatic code that aligns with the established standards and best practices of the target language.
* **Use Imports**: Add explicit imports instead of using fully qualified type names in source code across all languages (e.g., use `import com.google.cloud.spanner.Options;` instead of writing `com.google.cloud.spanner.Options.tag(...)` inline).


### 2. Rust-Specific Guidelines
* **Variable Naming**: Always use full words for variable names to ensure readability. Avoid abbreviations unless they are standard/common (e.g. `db` for database is allowed, but `rs` instead of `result_set` is **NOT** allowed).
* **Avoid `unwrap()` in Tests**: Try to avoid `unwrap()` in test files. Prefer using `.expect("clear error message description")` or returning a `Result` from the test function.
* **Explicit Assertions**: Add explicit, descriptive error messages for assertions in Rust code (e.g. use `.expect(...)` or custom assertion messages). Do not use `.wrap()`.


### 3. Extending the ChatOps Bot
The conversational benchmark runner parses issue comments into Cloud Run benchmark deployment configurations.
* **Adding a New Client Library or Benchmark Type**: Do **NOT** modify the prompt instructions (`.github/scripts/bot_instructions.md`) directly. The bot's lists of valid values are dynamically injected. To add support, open [.github/scripts/parse_chatops.py](file:///.github/scripts/parse_chatops.py) and update the whitelist sets `SUPPORTED_CLIENTS` and `SUPPORTED_BENCHMARKS` at the top of the file.
* **Adding a New Benchmark Option/Flag**: 
  1. In [.github/scripts/parse_chatops.py](file:///.github/scripts/parse_chatops.py), add the option key to the `RESPONSE_SCHEMA`, add the regex validation in `sanitize_run()`, and add the sanitized key to the returned dictionary.
  2. In [.github/workflows/gemini-chatops.yml](file:///.github/workflows/gemini-chatops.yml), extract the parameter from the runs JSON (e.g., `new_option=$(echo "$run" | jq -r '.new_option')`) and export it as an environment variable in the execution block (e.g., `NEW_OPTION="$new_option"`).
  3. In [run_benchmark.sh](file:///run_benchmark.sh), read the env variable and pass it to the benchmark container execution command.
